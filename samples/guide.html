How to use this guide

From the repo root, start the playground and run the first detector:

# land at the DuckDB prompt with the data loaded as `bill`
./run.sh

# CHECK — can this data even answer the question?
.read queries/config-change-cost-runaway/preflight.duckdb.sql

# LEARN — top subaccounts ranked, the 3 rules as pass/fail flags:
.read queries/config-change-cost-runaway/diagnostic.duckdb.sql

# TRUST — the detector, keeping only the confirmed hit:
.read queries/config-change-cost-runaway/query.duckdb.sql

In the diagnostic, the real runaway trips all three flags while normal accounts sit near a 1.0× step — that separation is the proof. Compare the detector's row to the expected finding below, then explore: change a threshold, group by servicename, look at the days around the onset.

Every pattern ships in these same three acts. Swap the query folder and the commands work for any of the sixteen.

Preflight is what makes a zero row mean something. Zero rows with every check PASS is a real, honest zero — your bill is clean on that pattern. Zero rows with any check FAIL means your data cannot answer the question at all, which is a blind spot, not a clean bill. Those are opposite conclusions and they look identical without it.

Check the whole corpus at once. python3 tools/verify_corpus.py runs all three acts for all sixteen detectors and prints what each one finds — the same inspection this repo is tested with.

The worked example — Config-Change Cost Runaway

Config-Change Cost Runaway

Config-Change Data-Processing Runaway

AWS High

On one AWS subaccount, per-GB data-processing spend (NAT-gateway bytes, cross-AZ transfer, traffic inspection) steps up sharply and stays elevated — while compute stays flat. That combination is the fingerprint of a networking/routing config change shipped without a cost guardrail, not organic growth. No single day looks alarming, which is why this kind of leak runs for weeks.

Two of the sixteen are not alarms

Worth knowing before you run them, because they behave differently on purpose. Scheduling Miss and Untagged Spend are posture measures, not anomaly detectors: they describe a property of the whole estate rather than finding one thing that is wrong.

MeasureCloudQueryExpected rows
Weekend cost barely drops (scheduling candidates)AWS · Azure · GCPScheduling Miss110
Untagged spend (tagging coverage)AWS · Azure · GCPUntagged Spend176

Those large counts are the correct answer, not a false positive. In this bill 147 of 185 resources genuinely bill flat across weekends — as most production infrastructure does — and neither query can know which of your resources were supposed to be shut down or tagged. Read them as a list to triage, not a finding to act on. Both queries cap output at 25 rows; remove the LIMIT to see the full population.

These queries teach you the shape of each leak so you can catch it yourself, free. DropInFinOps scores, ranks, and explains these signals across your clouds automatically — but the patterns are yours to keep.
